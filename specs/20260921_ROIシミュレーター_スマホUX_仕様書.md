## 4. 入力契約表（現状の挙動）

### 4.1 前提：`type="number"` の値正規化
HTML Standard の value sanitization により、`input[type=number]` の `.value` は **有効な浮動小数点数でない内容をすべて空文字に正規化**する。したがって「全角数字」「文字列」「単位付き」はすべて `""` として読み出され、`parseFloat("") → NaN → || 0 → 0` となる。`min="0"` は入力をブロックしない（フォーム検証用の属性であり、本ファイルに `<form>` も送信もないため実効性がない）。スピナーは `appearance: none`（L187-191）で非表示のため `step` も入力を拘束しない。

### 4.2 入力契約表

| # | 入力欄 | セレクタ / 属性 | 未指定（空欄） | 不正な値（全角数字・文字列・単位付き・マイナス） | 正常値 |
|---|---|---|---|---|---|
| 1 | 年商 | `#annualRevenue` / `number, value=50, min=0` | `""` → **計算に不使用**。`calculate()` は本欄を参照しない（L1760 のリスナー配列にのみ登場）。表示への影響ゼロ | 全角「５０」「abc」→ `""`。マイナス「-10」は値として読めるが未使用。いずれも影響ゼロ | 影響ゼロ。ラベル「参考値です（ROI計算には影響しません）」と整合 |
| 2 | 活動月・開始 | `#startMonth` / `select` 1〜12 | **発生しない**（既定 4、空 option なし） | **発生しない**（12択のみ） | `getActiveMonths()`: `s<=e → e-s+1`、`s>e → (12-s+1)+e`（年またぎ）。例 11→2 = 4ヶ月、5→5 = 1ヶ月 |

**根拠**: 本表は `calculate()`（L1540-1719）・`addMember()`（L1448-1493）・`getActiveMonths()`（L1435-1440）のコード読解と HTML Standard の value sanitization から導出し、**2026-09-21 に Playwright（Chromium）で全行を実測して訂正した**。

### 4.2.1 実測で判明した、コード読解からの2つの訂正（2026-09-21）

| # | 当初の記述（誤り） | 実測結果 |
|---|---|---|
| 1 | 全角数字は value sanitization により `""` になる | **Chrome は全角「５０」を半角 `50` に正規化して受け付ける**。`""` にはならない。文字列「abc」は記述どおり `""` になる。※iOS Safari 実機での挙動は未検証 |
| 2 | マイナス入力時に `workBracket` の width が負値になり、CSS 無効値として無視され直前の幅が残る | **バーの幅は崩れない**。幅は `REDUCTION_RATE` から算出される比率であり入力値の符号に依存しないため、`-50` を入れても `workBeforeBar:100% / workBracket:90% / workUsedTime:10% / workFreedTime:90%` のまま正常（実測） |

**マイナス入力時の実挙動（実測値・今回スコープ外だが記録）**

| 入力 | 表示される結果 |
|---|---|
| 月間稼働時間 `-50` | 年間総稼働 −350時間／チーム工数 −1,050時間／回収 1.7ヶ月 |
| 年収 `-600` | チーム人件費 ¥350,000（負の1人分が他2人を打ち消す）／工数削減 31万円 |
| 年間案件数 `-4` | 基本 ROI **−8.1倍**／年間効果差額 **−2,029万円** |
| 平均単価 `-500` | 同上 |

いずれも例外は発生せず、JS エラーは0件。ただし**公開ページで負の ROI が表示されうる**という事実は残るため、§8 の Could（負値クランプ・要社長確認）の判断材料とする。

`#annualRevenue` の非参照も実測で確認した（50→99999 に変更しても結果セクションの innerText が完全に同一）。

### 4.3 契約から導かれる制約 IN-1〜IN-3
- **IN-1**: `type="number"` を維持する。`type="text"` + `inputmode` に変更すると `parseFloat("50万") → 50`、`parseFloat("５０") → NaN` のように **正規化の責務が JS 側に移り、本表が無効化される**。`inputmode` は `type="number"` と併用する（キーボード選択のヒントであり、値の解釈を変えない）。
- **IN-2**: `inputmode="decimal"` は iOS で小数点付きテンキーを出し、**マイナス記号を出さない**。#4/#6/#7/#8 の負値リスクを副次的に下げる。`inputmode="numeric"` は小数点が出ないため、`step=0.5` の `#annualCases` や小数入力があり得る `#monthlyHours` には使わない。
- **IN-3**: 負値・ゼロ値の挙動は**現状のまま記録し、今回は変更しない**（§8 Could 扱い）。クランプ処理の追加は計算経路への介入であり、社長確認を要する。

### 5.0.1 検証手段の分類（2026-09-21 改訂・astra 指摘）

**Playwright の端末エミュレーションは viewport・タッチ・UA を再現するだけで、実機の OS キーボードや Safari の操作領域までは再現しない。**すべての AC を自動検証で証明することはできないため、AC を3種に分ける。

| 種別 | 対象 | 判定者 |
|---|---|---|
| **自動判定** | 寸法・色・コントラスト・DOM構造・数値の一致・横スクロール・印刷ページ数・コピー文字列 | Evaluator が Playwright で機械検証。**合否はここで決める** |
| **実機確認** | iOS の自動ズーム、ソフトキーボードによる遮蔽、小数点キーの表示、URLバー伸縮、ホームインジケータとの重なり | **自動検証では証明できない**。実機（対応 iOS / Safari バージョンを明記）で目視確認し、結果を記録する。未実施なら「未検証」と明記して合否を保留する |
| **設計評価** | 視覚言語の整合、情報の優先順位、破線の視認性 | 主観が残る。色・線種・寸法は自動判定に落とし、残りは目視評価として分離する |

### 5.0.2 ページ高・距離を測るときの固定条件

AC2-4-1 / AC2-4-3 の測定は、必ず次の条件で行う（条件が違えば数値は比較できない）。

- メンバー3名（既定）・全入力が既定値
- 折りたたみは**初期状態**（モバイルでは畳まれた状態）
- キーボードなし
- `deviceScaleFactor: 3`, `isMobile: true`, `hasTouch: true`

**メンバー追加後や説明を展開した後の高さは、この上限の対象外とする**（内容量が増えるのだから当然高くなる）。文字拡大時も、ページ高より**文字の欠落防止**を優先する。

### 5.0.3 根拠の訂正（astra 指摘）

- **AC1-2-4 の「8px 間隔」は WCAG 2.5.8 の要求ではない**。同基準が定めるのは 24×24 CSS px（または所定の例外）。44×44px と 8px 間隔は**本製品が自ら定める設計基準**である。仕様上そう扱う（WCAG を根拠に見せない）。
- **AC1-5-2 の「全子孫を一律に検査」は過剰**。非表示要素やインライン要素まで同条件で扱わず、**ページ全体（`documentElement.scrollWidth`）と、主要な入力・数値・注記**に対象を絞る。
- **AC3-3-4 の「増分80px以内」は AC2-4-3 と重複**し、読みやすさを犠牲にする誘因になる。参考計測に留め、合否条件から外す。

## 7. JS が依存する DOM 契約（壊してはならないもの）

### D-1 ID 契約
`calculate()` / `copySummary()` / 初期化コードが参照する ID は、**名前・個数・要素種別を変えてはならない**。

- **読み取り専用**: `startMonth`, `endMonth`, `monthlyHours`, `annualCases`, `unitPrice`, `teamList`, `addMemberBtn`, `summaryDoc`
- **リスナー登録のみ（値は未使用）**: `annualRevenue`
- **書き込み対象**（`setText` / `setHTML` / `setStyle` / `setAttribute` 経由）: `activeMonthsDisplay`, `annualHoursPerPerson`, `teamCount`, `teamAnnualHours`, `teamAnnualCost`, `workHeadline`, `workRateNote`, `workBeforeHours`, `workBeforeCost`, `workReducedBridge`, `workAfterHours`, `workFreedHours`, `workReducedTotal`, `workSavingTotal`, `workAfterCost`, `workBeforeBar`, `workBracket`, `workUsedTime`, `workFreedTime`, `workAfterBar`, `opportunityHours`, `opportunityRateNote`, `opportunityCaseChange`, `opportunityAddRevenue`, `opportunityAddedCases`, `opportunityUnitPrice`, `{conservative|basic|theory}{TotalCases|AddCases|Roi|Revenue|Saving|Fee|Profit}`, `basicPayback`, `scenarioAnnualCost`, `scenarioZeroNote`, `summaryRevenue`, `summarySaving`, `summaryFee`, `summaryProfit`, `summaryEquation`, `summaryCopyText`, `sumRoi`, `sumPayback`, `summaryWorkNote`, `summaryTeamAssumption`, `summaryPeriodAssumption`, `summaryCurrentAssumption`, `summaryRateAssumption`

### D-2 `.team-row` の構造契約
- `calculate()` は `document.querySelectorAll('.team-row')` を走査し、各行の `.role`（`value` が `leader`/`member`）と `.salary`（数値入力）を**必須**として読む。この2クラスは行内に1つずつ存在すること。
- `.member-hours` / `.member-hourly` は `if (el)` でガードされており任意。
- `.remove-btn` のガードは `document.querySelectorAll('.team-row').length > 1`。**`team-row` クラスをメンバー行以外に流用してはならない**（件数判定が壊れる）。
- 行マークアップの唯一の生成元は `addMember()` のテンプレートリテラル（L1454-1469）。構造変更はここで行い、`.team-row { grid-template-columns: 140px 1fr 140px 40px }`（L234）と整合を取る。列数を変える場合は PC 側の `grid-template-columns` も同時に更新すること。

### D-3 イベント配線の契約
- L1760-1763 で 6 つの ID に `input` と `change` の**両方**を登録している。`<select>` では両方が発火し `calculate()` が2回走るが、これは意図的に許容されている状態である。
  - `input` を外すと数値入力の即時反映が失われる（S2-1 のライブ更新が壊れる）。
  - `change` を外すとプログラム的変更・ステップ操作を取り逃す。
  - **どちらも外さない**。
- 新しい入力コントロールを追加する場合は、この配列に ID を追加する方式に揃える（個別に `addEventListener` を書き足さない）。
- `.role` / `.salary` / `.remove-btn` のリスナーは `addMember()` 内で行ごとに登録される（L1477-1490）。行を再生成する実装に変えると二重登録の危険があるため、既存の「生成時1回登録」方式を維持する。

### D-4 ヘルパー契約
`setText` / `setHTML` / `setStyle` / `setAttribute`（L1499-1514）はすべて `if (element)` で null ガードされている。**新しい表示先 ID を `calculate()` の末尾に追加しても、その要素が存在しないビューポートで例外にならない**。S2-1 の固定バーはこの性質を利用してよい。

### D-5 数値フォーマット契約
`formatNumber` / `formatMoney` / `formatMultiple`（L1515-1537）は表示規則そのものであり変更禁止。特に `formatMultiple` の「10倍以上は整数表示」ロジック（L1532-1535 のコメント参照）と `formatMoney` の億・万の桁処理は死守数値の生成に直結する。

### D-6 `#summaryDoc.innerText` 契約（コピー機能）
- `copySummary()`（L1722-1734）は `#summaryDoc` の `innerText` をそのままコピーする。
- **`#summaryDoc` の内側に新しい要素を追加してはならない**。追加した文言はすべてコピー結果に混入する。
- `innerText` は CSS のレンダリング状態に依存する: `display: none` の内容は除外されるが、`visibility: hidden` や `clip` による視覚的隠蔽は**除外されない**。`.summary-copy-text`（L863-876）はこの性質に依存して式のテキストを供給している。
- `.summary-equation` の値は CSS の `content: attr(data-value)` で描画されており、**`innerText` に入らない**。これは二重掲載を避けるための設計（L1353-1355）。実テキスト化してはならない。
- S2-1 の固定バーは `#summaryDoc` の外側、かつ `.container` の外側に置く。

### D-7 追従要素の配置制約
- `.container` は `overflow: hidden` + `border-radius: 16px`（L35-42）。この内側に置いた `position: sticky` は追従せず、はみ出し部分は clip される。
- `.container` に `transform` / `filter` / `will-change` は適用されていないため、`position: fixed` は正しくビューポート基準で機能する。
- したがって固定要素は **`<body>` の直下・`.container` の外側**に配置する。これにより D-6（コピー汚染回避）と AC3-4-4（印刷抑制の一行化）も同時に満たせる。
- 固定バーの高さぶんの下余白は、`@media (max-width: 700px)` ブロック内で `body` 側に確保する（現行 `body { padding: 10px }` L1018 を起点に）。PC の `body { padding: 20px }`（L32）は変更しない。

   └─ 44px化・16px化・inputmode・チーム行レイアウト

        ↓  （バー存在下での遮蔽・印刷・コピーを検証するため後続）

- 単一ファイルのため**並列実行は不可**。上から順に直列で進める。
